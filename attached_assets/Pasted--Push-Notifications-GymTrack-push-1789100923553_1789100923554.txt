# תוכנית עבודה: תיקון מלא של מערכת ה-Push Notifications ב-GymTrack

## הקשר
בוצע אודיט למערכת ה-push. התשתית קיימת (FCM, טוקנים, Edge Function, הרשאות), אבל **אין הוכחה שהתראה הגיעה בפועל למכשיר סגור**, וקיימים כמה פערים קונקרטיים. המטרה של הפרומפט הזה: לקחת סוכן/מפתח ולהוביל אותו צעד-צעד עד למצב שבו יש **הוכחה אמיתית שהכול עובד**, לא רק שהקוד קיים.

---

## הוראות לסוכן שמקבל את הפרומפט הזה

בצע את השלבים בסדר הזה. אחרי כל שלב, דווח בפירוש: **הצליח / נכשל / לא ניתן לאמת**, ואל תמשיך לשלב הבא אם שלב קודם נכשל בלי לדווח על כך במפורש. אל תניח שקוד קיים = קוד עובד. בכל שלב שבו נדרש טסט על מכשיר אמיתי — אל תסמן אותו כ"הושלם" בלי תוצאה בפועל (צילום מסך / לוג / תיאור מפורש של מה שקרה על המכשיר).

---

## שלב 0 — הקפאת מצב (Safety net)
1. ודא שיש גיבוי/snapshot של מסד הנתונים לפני כל שינוי.
2. ודא שהקוד המקומי הנוכחי של `send-fcm-notification` נמצא ב-git עם commit ברור, לפני שמפרסים אותו מחדש.

---

## שלב 1 — סנכרון הפונקציה שרצה בפרודקשן עם הקוד המקומי
**בעיה:** הגרסה שרצה בפועל (v16) ישנה מהקוד המקומי — חסר `deepLink`, חסרה הגבלת קואצ'ים, ה-payload שונה.

**משימות:**
1. סקור diff מלא בין הגרסה החיה לגרסה המקומית של `send-fcm-notification`.
2. פרוס (`supabase functions deploy send-fcm-notification`) את הגרסה העדכנית.
3. ודא לאחר הפריסה: מספר הגרסה עלה (למשל v17+), ושה-JWT verification עדיין מופעל.
4. הרץ קריאה בודדת לפונקציה (עם משתמש טסט) וודא שה-payload שחוזר תואם לקוד המקומי (כולל `deepLink`).

**קריטריון הצלחה:** גרסת production זהה ל-repo, מאומת ע"י diff נקי.

---

## שלב 2 — אימות אמינות ה-credentials של Firebase בצד השרת
**בעיה:** לא אומת שה-Edge Function שרץ בפועל מחזיק private key תקין, client email תואם, ו-service account עם הרשאות שליחה.

**משימות:**
1. בדוק (ללא חשיפת הערכים בלוג/צ'אט) שקיימים ב-Supabase secrets: `FIREBASE_CLIENT_EMAIL`, `FIREBASE_PRIVATE_KEY`, `FIREBASE_PROJECT_ID`.
2. ודא ב-Google Cloud Console / Firebase Console:
   - Firebase Cloud Messaging API מופעל בפרויקט.
   - ה-service account מוגדר עם תפקיד (role) שמאפשר שליחת FCM (למשל `Firebase Cloud Messaging API Admin` או שקול).
   - ה-private key תקף (לא פג/מבוטל).
3. הרץ טסט יבש: קריאה ל-Edge Function שמנסה להוציא OAuth access token מול Google, ובדוק שההחזרה מצליחה (status 200 + טוקן תקין), לא רק שהקוד "לא זרק שגיאה".
4. אם יש כשל — תעד את קוד השגיאה המדויק שחוזר מגוגל (401/403/400) ותקן בהתאם (private key שגוי / role חסר / project ID לא תואם).

**קריטריון הצלחה:** קריאת OAuth token מוצלחת מתועדת בלוג, לא בהנחה.

---

## שלב 3 — רישום טוקן אמיתי של קואצ' על מכשיר אמיתי
**משימות:**
1. התחבר כ-Coach על מכשיר Android אמיתי (build שכולל `google-services.json` תואם).
2. אשר הרשאת התראות.
3. ודא בטבלת `push_tokens` שנוצרה שורה חדשה עם `user_id` נכון, `platform: android`.
4. חזור על התהליך על מכשיר iOS אמיתי (לא סימולטור) — כולל אימות ש-APNs מוגדר ב-Apple Developer וב-Firebase, וש-provisioning profile כולל push entitlement.
5. חזור על התהליך גם ב-Web (דפדפן נתמך), כולל רישום Service Worker מוצלח.

**קריטריון הצלחה:** שלושה טוקנים אמיתיים (Android, iOS, Web) קיימים בטבלה, כל אחד משויך למכשיר אמיתי שנבדק.

---

## שלב 4 — טסט E2E על שני חשבונות ומכשירים אמיתיים (הטסט הקריטי)
בצע בדיוק את הפרוטוקול הבא — הוא הדרך היחידה לדעת אם המערכת "עובדת" ולא רק "קיימת":

### הגדרה
- חשבון 1: Owner. חשבון 2: Coach. שני מכשירים פיזיים נפרדים אם אפשר.
- שימוש ב-build פרודקשן (לא dev server מקומי).

### צד המכשיר של הקואצ'
1. התחבר כ-Coach.
2. פרופיל → התראות → הפעל.
3. אשר הרשאת OS/דפדפן.
4. ודא שה-UI מדווח שההתראות הופעלו בהצלחה.
5. **סגור לגמרי** את כל הטאבים של GymTrack, או העבר את האפליקציה הנייטיבית לרקע.
6. נעל את המסך.

### צד המכשיר של ה-Owner
7. התחבר כ-Owner.
8. פתח אזור שידור הודעות.
9. בחר "כל הקואצ'ים".
10. שלח הודעה ייחודית לזיהוי, לדוגמה: `PUSH_TEST_<תאריך>_<מספר סידורי>`.

### תוצאה מצופה (חובה לתעד בפועל, לא להניח)
11. מכשיר הקואצ' מציג התראה בזמן שהאפליקציה סגורה.
12. תוכן ההתראה תואם בדיוק לטקסט שנשלח.
13. הקשה על ההתראה פותחת את GymTrack.
14. תוצאת השליחה בשרת מדווחת הצלחה (לא `sent: 0` ולא כשל).
15. לוגים של ה-Edge Function מראים בקשת FCM מוצלחת.

### טסט ריבוי מכשירים
16. אותו קואצ' מתחבר ממכשיר שני, מפעיל התראות שם גם.
17. סוגרים את GymTrack בשני המכשירים.
18. שולחים broadcast נוסף.
19. **שני** המכשירים אמורים לקבל את ההתראה.

### טסט בקרה (חשוב מאוד — מבדיל בין Realtime לבין Push אמיתי)
20. פעם אחת עם טאב פתוח, פעם אחת עם המכשיר סגור לגמרי, לאותה שליחה.
21. פרשנות:
    - טאב פתוח מקבל התראה → מסלול Realtime/foreground עובד (זה **לא** מוכיח push אמיתי).
    - מכשיר סגור מקבל התראת OS → מסלול FCM האמיתי עובד.
    - טאב פתוח עובד אבל מכשיר סגור לא → יש בעיה ב-push המרוחק, גם אם הכול "נראה תקין" בקוד.

**קריטריון הצלחה לכל התוכנית:** שלב 21 מראה בבירור שמכשיר סגור מקבל התראה אמיתית — לא רק מסלול foreground.

---

## שלב 5 — סגירת פערי אמינות (לביצוע אחרי שה-E2E עובד פעם אחת)
1. **Web token refresh:** הוסף listener ייעודי ל-refresh טוקן ב-web (לא רק בזמן הפעלת ה-setup הראשוני).
2. **מניעת מחיקת טוקנים חוצת-מכשירים:** תקן את פעולת "כיבוי התראות" כך שתמחק רק את הטוקן של המכשיר הנוכחי, לא את כל שורות ה-`push_tokens` של המשתמש.
3. **הפרדת סטטוסים ב-UI:** הצג בבירור "ההודעה נשמרה" לעומת "ההתראה נשלחה בהצלחה" כשני מצבים נפרדים, כולל טיפול במקרה כשל אסינכרוני.
4. **(אופציונלי, לפי דרישת המוצר):** הוסף מסלול Owner → קואצ' בודד דרך `coach_messages`, אם יש צורך עסקי במסלול ישיר ולא רק broadcast.

---

## דיווח סופי נדרש
בסיום, הפק סיכום קצר שכולל לכל שלב (0–5):
- סטטוס: הושלם / נכשל / לא רלוונטי
- הוכחה קונקרטית (מספר גרסה, תוצאת לוג, צילום מסך, תיאור תוצאה במכשיר)
- אם נכשל — מה בדיוק נכשל ומה הצעד הבא לתיקון

אל תסכם "הכול עובד" בלי שסעיף 21 (טסט הבקרה במכשיר סגור) הניב תוצאה מתועדת בפועל.
