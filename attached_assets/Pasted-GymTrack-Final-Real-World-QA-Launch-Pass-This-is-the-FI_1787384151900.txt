GymTrack — Final Real-World QA & Launch Pass

This is the FINAL QA and launch pass for the GymTrack / My Routine application.

Treat the current project and its connected Replit Secrets as the source of truth.

Do NOT create another general audit based only on source inspection.

The application is already running in Preview.

Your job now is to actually use the application, test it as all three roles, find every real problem, fix the code directly, and leave the project ready for final deployment.

1. USE THE REAL APPLICATION

Open the running GymTrack Preview and test the actual UI.

Do not assume a feature works because its code exists.

Do not assume a feature works because a previous AI report says it works.

For every important feature:

1. Open it.
2. Click the relevant buttons.
3. Enter realistic data.
4. Save it.
5. Refresh.
6. Navigate away and return.
7. Log out.
8. Log back in.
9. Verify the data is still correct.

Fix any failure you discover.

2. TEST ALL THREE ROLES

Test the application separately as:

* Owner
* Coach
* Client

Verify that each role sees only the functionality and data it should see.

Owner

Verify:

* Owner dashboard
* User management
* Coach management
* Client management
* Coach/client assignment
* Role management
* Owner-only functionality
* Profiles
* Programs
* Workouts
* Nutrition
* Messages
* Measurements
* Feedback

A Coach or Client must never see Owner functionality.

Coach

Verify:

* Coach dashboard
* Assigned clients
* Client profiles
* Client programs
* Client workout history
* Client measurements
* Client nutrition
* Client feedback
* Coach messages
* Recipes
* Exercise management

Verify that a Coach cannot access an unassigned client’s private data.

Client

Verify:

* Client dashboard
* Profile
* Assigned coach
* Workout program
* Workout player
* Workout history
* Nutrition
* Food search
* Fiber tracking
* Favorites
* Custom foods
* Custom exercises
* Measurements
* Feedback
* Coach messages
* Password recovery

A Client must never see another client’s data or Owner/Coach administration tools.

3. AUTHENTICATION

Test:

* Signup
* Login
* Logout
* Refresh while logged in
* Close/reopen the app
* Login again
* Password recovery
* Password reset
* Redirect after recovery

Verify that Supabase authentication is the source of truth.

Verify that logging out completely clears the previous user’s private application state.

Then log in as another user and confirm that no previous user’s data appears.

4. SUPABASE PERSISTENCE

For each important feature, verify actual persistence through Supabase.

Test:

* Custom foods
* Custom exercises
* Measurements
* Feedback
* Messages

If a save fails, show the user an error instead of reporting success.

7. MEASUREMENTS

Verify all measurement functionality that actually exists.

Do not claim full body measurements work unless the UI and persistence actually support them.

If something is present in the UI but does not work, fix it.

If a feature is genuinely absent, report it clearly.

8. MESSAGES AND FEEDBACK

Test:

* Coach → assigned Client message
* Client viewing the message
* Unauthorized Coach → Client attempt
* Client feedback submission
* Coach feedback viewing

Do not allow cross-client access.

Do not claim a message or feedback was sent unless Supabase confirms the write.

9. SECURITY

Do not weaken security.

Verify:

* RLS remains enabled.
* Owner permissions remain Owner-only.
* Coach permissions remain limited to assigned clients.
* Client permissions remain limited to their own data.
* Role escalation is impossible from the client.
* coach_id cannot be arbitrarily changed by a Client.
* Privileged RPCs remain protected.
* SECURITY DEFINER functions remain hardened.
* No service-role key is exposed.
* No private Supabase credentials are placed in frontend code.

Do NOT disable RLS to make something work.

Do NOT create broad anonymous permissions.

Do NOT replace secure RPCs with insecure frontend updates.

While actually using the application:

* Check browser console.
* Check network failures.
* Check Supabase errors.

* Check missing assets.
* Check invalid states.

Fix all errors caused by normal usage.

Do not simply document an error that can be fixed.

If it is already implemented, test and fix it.

If it is required by the current product, implement it properly.

If it is not required for the current launch, leave it alone and clearly state that.

Do not create unnecessary database changes.

13. DATABASE

Do NOT blindly run migrations 10 or 11.

First compare them against the actual live schema.

Apply only genuinely missing database changes.

Never:

* Drop existing tables
* Recreate existing tables
* Delete existing user data
* Disable RLS
* Replace working policies unnecessarily
* Duplicate existing columns
* Create duplicate tables

If a migration is already applied, do not apply it again.

14. BUILD AND VALIDATION

After all fixes:

Run:

npm run build

npm run lint

Make sure:

* Build succeeds.
* Lint has zero errors.
* No new warnings are introduced unnecessarily.
* Preview starts successfully.

15. FINAL ZIP

After everything is finished:

Create a NEW ZIP containing the final updated source code.

The ZIP must:

* Contain the actual latest source.
* Contain all required migrations.
* Contain the audit/report.
* NOT contain .env.local.
* NOT contain service-role keys.
* NOT contain private credentials.
* NOT contain unnecessary build/dependency directories.

Verify the ZIP contents before finishing.
