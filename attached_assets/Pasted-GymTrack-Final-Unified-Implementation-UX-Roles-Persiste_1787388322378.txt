GymTrack — Final Unified Implementation, UX, Roles, Persistence & QA

אני רוצה להשלים עכשיו את GymTrack כמוצר אמיתי, יציב ומוכן לשימוש.

עבוד אך ורק על בסיס הקוד הקיים.

אל תבנה את האפליקציה מחדש.

אל תשנה Supabase, RLS, migrations, RPCs או security ללא צורך אמיתי ומאומת.

לפני כל שינוי:

1. בדוק מה כבר קיים.
2. בדוק מה כבר עובד.
3. בדוק מה חסר.
4. בדוק מה כבר נשמר ב־Supabase.
5. רק לאחר מכן בצע את השינוי המינימלי הנדרש.

המטרה היא להשלים את GymTrack ולא ליצור מימוש מקביל.

⸻

1. הפרדה מלאה בין Owner / Coach / Client

אני רוצה שלכל Role תהיה חוויית מוצר שונה וברורה.

Owner

כאשר המשתמש הוא owner, הוא צריך להיכנס ל־Owner App אמיתי ולא ל־Client App עם כמה הרשאות נוספות.

צריך להיות:

* Owner Dashboard
* Owner Navigation
* ניהול מאמנים
* ניהול מתאמנים
* חיפוש מתאמנים
* חיפוש מאמנים
* צפייה בפרופילים
* שיוך מתאמן למאמן
* החלפת מאמן
* שינוי Role
* צפייה בתוכניות
* צפייה באימונים
* צפייה בהיסטוריית אימונים
* צפייה במדידות
* צפייה בתזונה
* צפייה במשובים ובדיקות
* ניהול הפונקציות הניהוליות שכבר קיימות באפליקציה

ה־Owner UI צריך להרגיש כמו מערכת ניהול נפרדת.

לא Client App עם עוד כמה כפתורים.

כאשר Role משתנה ל־Owner, המשתמש צריך לעבור ל־Owner App.

4. שינוי Role

כאשר Owner משנה:

Client → Coach

המשתמש צריך לקבל Coach App לאחר שה־Role מתעדכן.

כאשר:

Coach → Client

המשתמש צריך לקבל Client App.

כאשר:

User → Owner

המשתמש צריך לקבל Owner App.

ה־Role חייב להגיע מה־Supabase profile/session האמיתי.

אסור להשתמש ב:

* username hardcode
* email hardcode
* localStorage כ־source of truth
* demo role
* חריגים לפי משתמש
* logic מיוחד עבור Maya או משתמש אחר

5. Maya2003yos — קריטי

maya2003yos לא אמורה להיות Owner.

כרגע לאחר התחברות היא מוצגת כ־Owner.

לפני שינוי כלשהו:

בדוק בפועל:

* Auth user ID
* profiles.role
* profiles.coach_id
* is_owner()
* ה־Role שהאפליקציה מקבלת
* ה־Role שה־UI מציג

אם ה־DB באמת מחזיר owner:

אל תשנה את ה־DB באופן אוטומטי.

דווח:

* מה הערך האמיתי
* מאיפה הוא מגיע
* למה הוא owner
* האם מדובר בנתון DB או בבעיה בצד הלקוח

אם ה־DB אינו owner אבל האפליקציה מציגה Owner:

מצא את מקור הבעיה ותקן אותו.

אסור ליצור שום logic מיוחד עבור Maya.

6. Persistence — הדבר הכי חשוב

כל דבר שאני או Coach כותבים, עורכים או מעדכנים עבור מתאמן חייב להישמר באמת.

הזרימה חייבת להיות:

Edit → Save → Supabase → Refresh → עדיין קיים

וגם:

Edit → Save → Logout → Login → עדיין קיים

Supabase צריך להיות מקור השמירה האמיתי.

אסור להסתמך על:

* React state בלבד
* localStorage
* mock data
* demo data
* נתונים זמניים

אם המשתמש עורך נתון של מתאמן ולוחץ Save, הנתון חייב להיכתב ל־Supabase בהצלחה.

אם Supabase מחזיר שגיאה:

* אל תציג כאילו השמירה הצליחה
* הצג שגיאה ברורה
* שמור על הנתון הקיים
* טפל בשגיאה בצורה נכונה

8. Rep Range — חייב להיות טווח

צריך לתמוך ב:

* Fixed reps
* Rep range
* repMin
* repMax

הנתונים צריכים להישמר במבנה הקיים.

אין צורך ליצור עמודות DB חדשות אם המבנה הקיים כבר תומך בזה.

ה־UI צריך להציג:

8–12 reps

ולא רק:

8 reps

או:

12 reps

יש לוודא שהטווח נשמר לאחר:

Save → Refresh → Logout → Login

אם המשתמש מזין:

8–12

הערך חייב להישאר 8–12 בכל טעינה מחדש.
